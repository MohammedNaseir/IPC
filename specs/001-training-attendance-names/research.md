# Phase 0 Research: Training Attendance Without Practitioner Linkage

All Technical Context unknowns are resolved below. No `NEEDS CLARIFICATION` items remain.

## R-001 — How to read `.xlsx` uploads

**Decision**: add `read-excel-file` 9.3.10 (MIT) and import it server-side only, via its
`read-excel-file/node` entry point. Verified on the registry: that subpath exports CJS, ESM and
TypeScript types, so it works in the Node runtime the app already uses.

**Rationale**: `.xlsx` is a ZIP of XML, so some reader is unavoidable once the spec requires real
Excel files (FR-011). `read-excel-file` is 2.5 MB unpacked with 4 dependencies and does exactly
one job — read a sheet into rows. Its narrow surface is the cheapest way to add the capability
without widening the project's attack surface, which matters because the parser consumes
untrusted uploads.

**Alternatives considered**:
- `exceljs` 4.4.0 — read *and* write, which would also give an `.xlsx` template. Rejected: 22 MB
  unpacked and 9 dependencies (`archiver`, `unzipper`, `jszip`, `saxes`, `fast-csv`, `tmp`…) to
  parse one text column. Its writer only becomes worth that cost if a styled, multi-sheet export
  is needed later.
- `xlsx` (SheetJS) 0.18.5 — **rejected on security grounds**. The npm-published version is from
  before the project moved distribution off npm, and the prototype-pollution and ReDoS fixes exist
  only in later releases that were never published there. Adding a dependency whose newest npm
  version is known-vulnerable contradicts the constitution's security posture.
- `node-xlsx` — a thin wrapper around SheetJS, so it inherits the same problem.
- Hand-rolled ZIP + SpreadsheetML parser — rejected: far more code and far more risk than the
  library it replaces, for no benefit.

**Follow-up required at install time (Principle V evidence)**: run `npm audit` after adding the
dependency and record the result; if it reports a vulnerability in this package or its tree,
re-open this decision before building on it.

## R-002 — Template format, and parsing `.csv`

**Decision**: serve the template as UTF-8 **CSV with a BOM** from a route handler — a single
header cell `الاسم`, one name per row. Accept both `.xlsx` and `.csv` on import. Parse CSV with a
small in-repo single-column reader (strip BOM, split lines on `\r\n`/`\n`, unwrap one level of
double quotes, take the first field), not a CSV library.

**Rationale**: this removes the need for a spreadsheet *writer* entirely. Excel opens a
BOM-prefixed UTF-8 CSV directly and preserves the Arabic header, and the project already relies on
exactly that convention in the KPI export (`src/app/api/reports/kpis/route.ts` prefixes `﻿`).
For a one-column file, the quoting rules that justify a CSV library do not arise: a person's name
containing a comma is handled by the single quote-unwrap step, and everything after the first
field is ignored by design.

**Alternatives considered**:
- `.xlsx` template generated by `exceljs` — rejected with R-001; it would drag the writer in purely
  for cosmetics.
- A static `.csv` file in `public/` — rejected: `public/` is served without authentication and the
  project deliberately keeps served artifacts behind route handlers; a generated response also
  keeps the header text in one place with the parser that validates it.
- Accepting `.xls` (legacy binary) — out of scope per the spec's assumptions.
- A CSV library (`fast-csv`, `papaparse`) — rejected as unjustified for one column.

## R-003 — Enforcing "headcount XOR names"

**Decision**: enforce at three levels. (1) A CHECK constraint so each row is either a name or a
headcount, never both and never neither. (2) A partial unique index on `trainingId` where the row
is a headcount, so a training cannot hold two headcount rows. (3) Application logic in the write
path, which replaces a training's whole attendance set inside one transaction, so a training never
holds a headcount row and name rows simultaneously.

**Rationale**: the per-row invariants are cheap and permanent in SQL, and they close the door on a
future code path or a manual query creating the ambiguous state this feature exists to remove.
The cross-row "no mixing" rule needs either a trigger or a transactional replace; the replace is
already how the current code behaves (`deleteMany` then `createMany`), so it adds no complexity.

**Alternatives considered**:
- A database trigger for the cross-row rule — rejected for now as more machinery than the
  invariant needs, given every write already replaces the full set atomically. Reconsider if a
  future feature starts appending attendance incrementally.
- Application-only enforcement — rejected: Prisma cannot express these invariants, but that is an
  argument for raw SQL in the migration, not for leaving the database permissive.
- Splitting attendance into two tables (one for headcount, one for names) — rejected: it would
  move the exclusivity problem into a cross-table concern and churn every read path for no gain.

## R-004 — Migration order for dropping the practitioner link

**Decision**: one migration, in this order: add `attendeeName TEXT`; backfill it from
`Practitioner.name` for every row that still has a `practitionerId`; drop the foreign key and the
`practitionerId` column; add the CHECK constraint; add the partial unique index. Write it as raw
SQL, using `prisma migrate diff` output as the starting point for the column/FK statements and
hand-adding the backfill and the two constraints.

**Rationale**: FR-016 requires documented attendance history to survive as names, so the backfill
must run while the link still exists — hence before the drop. The constraints must be added after
the backfill, because rows that carried a `practitionerId` have no name until it completes and
would violate the CHECK. Production currently holds 0 practitioner-linked rows (verified), so the
backfill is a no-op there, but it is correctness insurance for any other environment.

**Alternatives considered**:
- Dropping the column and discarding linked rows — rejected: silently destroys attendance evidence
  in a compliance product, and the spec explicitly requires conversion.
- Two migrations (backfill, then drop) — rejected: the intermediate state is never deployed, so
  splitting only creates a window where both representations exist.
- `prisma db push` — rejected: the constitution requires a committed migration for every schema
  change.

## R-005 — Where the uploaded file is handled

**Decision**: the file is received by a Server Action, parsed in memory, and discarded. It is never
written to `UPLOADS_DIR`, never recorded in `StoredFile`, and no part of it is returned to the
client. Only extracted names and counts are persisted.

**Rationale**: the import is a data-entry channel, not a document the product keeps. Not storing it
means the stored-file allowlist, magic-byte checks and access-scoping rules stay exactly as they
are, with nothing weakened to admit spreadsheets. The 9 MB Server Action body limit already in
`next.config.ts` bounds the input, comfortably above a 1,000-name file.

**Alternatives considered**:
- Storing the source file as an attachment for provenance — rejected as scope the spec does not
  ask for; it would require adding `.xlsx`/`.csv` to the stored-file allowlist and new retention
  rules. Worth revisiting only if auditors ask for the original sheet.
- A dedicated upload route handler instead of a Server Action — rejected: the action path already
  carries session, scope and audit conventions, and the UI needs the summary as a return value.

## R-006 — Failing loudly on practitioner references (FR-005)

**Decision**: the attendance write path explicitly rejects any submission carrying a
`practitionerId`/`practitionerIds` field with a validation error, rather than ignoring unknown
fields.

**Rationale**: FR-005 demands the old mode be refused rather than silently dropped. A stale client
bundle, a cached page, or a replayed request would otherwise appear to succeed while recording
nothing — the worst outcome for an attendance record. An explicit rejection surfaces it.

**Alternatives considered**:
- Ignoring the field (zod's default strip behaviour) — rejected per FR-005.
- Accepting it as an alias for a name lookup — rejected: that is the linkage being removed.

## R-007 — Duplicates and count derivation

**Decision**: keep duplicate names as separate rows; derive the reported attendee count as the
number of name rows, or the headcount value when the training is in headcount mode.

**Rationale**: two attendees can genuinely share a name, and de-duplicating would under-report
attendance — a silent data loss in exactly the number that feeds the FR-41 KPIs. Deriving the
count from rows keeps a single source of truth and matches the current query behaviour (names plus
headcount summed), which reduces to the same result now that the two modes are exclusive.

**Alternatives considered**:
- De-duplicate case-insensitively on import — rejected: hides real attendees and would need an
  override path.
- Store a separate `attendeeCount` column — rejected: a second source of truth that can disagree
  with the rows, which FR-017 forbids.

## R-008 — Import summary and skip reasons

**Decision**: the action returns a structured summary — imported count, skipped count, and a
per-reason breakdown (`blank`, `too_long`) with row numbers for the non-blank rejections — and the
whole import commits atomically. Invalid *files* (unsupported type, unopenable, wrong header, no
names) are refused before any write, leaving existing attendance untouched.

**Rationale**: FR-013 requires imported/skipped counts and reasons; FR-014 requires existing data
to survive a rejected import. Row numbers make a 200-row sheet debuggable by the coordinator
instead of requiring trial and error. Committing atomically avoids a half-imported list that looks
complete.

**Alternatives considered**:
- Partial commit with a warning list — rejected: a partially imported attendance record is worse
  than a refused one, because the count looks plausible.
- Counts without reasons — rejected by FR-013.

## R-009 — Does the trainings screen still need practitioners?

**Decision**: stop loading practitioners on the trainings page and drop the prop. Verified that
`TrainingsView` uses `practitioners` only for the attendance picker and its selection state; the
practitioner roster keeps its own screen (`/assets`), which is unaffected.

**Rationale**: leaving a data load feeding nothing costs a query per page view and misleads the
next reader into thinking a dependency still exists.

**Alternatives considered**: keeping the prop for a future "suggest names" affordance — rejected as
speculative, and suggesting committee members as attendees is precisely the confusion D-001 ends.

## R-010 — Verification without a test framework

**Decision**: verify with the standard gates (`npm run typecheck`, `npm run lint`,
`npm run build`) plus a scripted harness against a built server and a scratch database, covering
the import paths, the mode-exclusivity rule, the practitioner-reference rejection, and a
cross-hospital negative test with a matching positive control. Rehearse the migration on a scratch
database and confirm the backfill with a seeded practitioner-linked row before considering it for
production.

**Rationale**: the repo has no test framework and no CI, so Principle V is satisfied by recorded
evidence rather than a suite. The negative/positive pairing is required by the constitution, and
this project has already had a false pass caught by exactly that pairing.

**Alternatives considered**:
- Introducing a test framework as part of this feature — a genuine improvement, but it is separate
  scope and would expand this change well beyond the spec; recommend it as its own feature.
- Manual clicking only — rejected: the cross-hospital and rejection cases cannot be exercised
  through the UI, since the UI no longer offers the removed mode.
